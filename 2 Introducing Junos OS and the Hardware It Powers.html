Module 1

Junos OS Architecture

Key Architectural Advantages

  • Modular software architecture: Junos OS is NOT a monolithic code base. Composed of many small, independent processes.
  • If one process crashes, all other processes continue running normally; the failed process restarts independently — no system-wide disruption.
  • Hardware separation for transit vs. device-destined traffic: transit traffic (forwarded packets) and management/protocol traffic are handled by separate hardware.
  • This hardware separation protects transit forwarding even if the control plane is overwhelmed by management traffic or protocol events.

If a routing protocol process enters a CPU loop or the RE is flooded with management requests, transit traffic forwarding continues uninterrupted — the PFE operates independently of the RE.

Module 2

Hardware & Chassis Types

Chassis Fundamentals

  • Chassis: the physical device — specifically, the outer case of the device.
  • Two primary categories: Fixed Port Chassis and Modular Chassis.
  • U (Rack Unit): standard height measurement for rack-mountable devices. Larger U = more performance, higher port density, and sometimes more features.

Fixed Port Chassis

  • Physical interfaces are built directly into the chassis — cannot be changed or expanded.
  • Contains a single built-in Routing Engine — not replaceable, not hot-swappable.

MX-204 (Fixed Port Example)

  • Compact form factor (~1U); interfaces built into the faceplate.
  • Available interface types: QSFP, SFP+, SFP transceivers.
  • Dedicated out-of-band management port (RJ-45) and console port.
  • Common use: enterprise edge, small service provider deployments.

Modular Chassis

  • Contains large empty slots designed to accept line cards.
  • Line cards: circuit boards inserted into slots; each adds ports and dedicated packet-processing ASICs.
  • Services line cards: line cards providing additional services (NAT, encryption) beyond port connectivity.
  • Line cards are typically hot-swappable — inserted/removed without powering down the chassis.

MX-480 (Modular Example)

  • Multiple line card slots; scales to very high port densities.
  • Routing Engine module in dedicated slot; may support redundant RE for high availability.
  • Slot numbering starts at 0 (zero-indexed).
  • Common use: large service provider edge/core, high-density enterprise.
⚠ Exam Distinction

Fixed chassis RE is NOT hot-swappable. Modular chassis Routing Engines and line cards typically ARE hot-swappable. Know this difference.

Routing Engine (RE)

  • The RE is the control plane CPU board running Junos OS software.
  • Manages: routing protocols, routing/forwarding table creation, system management, chassis management.
  • RE communicates with the PFE to download the forwarding table derived from the routing table.
  • In fixed chassis: one RE, built in, not removable.
  • In modular chassis: RE is a separate module; supports redundant RE.
  • RE connects directly to the management and console ports.

IP Addressing — /24 Subnet

  • /24 subnet mask = 255.255.255.0 — 24 bits network, 8 bits for hosts.
  • /24 provides 254 usable host addresses (256 − network address − broadcast).
  • Default gateway: router IP used by hosts to reach external networks.
  • In lab: SSH to any router IP on the management network — all reachable via the management default gateway.
💡 SSH to Any Router IP

All lab routers are on the same management /24. SSH to any of them using their management IP. The management default gateway routes within the management network.

SSH Connection Details

  • SSH version in use: SSHv2. Default TCP port: 22.
  • Provides: encrypted session, remote command execution, SCP/SFTP file transfer.
  • Shared login: lab environments may share a single username/password. Production: individual accounts per user.
  • Authentication: password OR SSH key pair (public/private key — more secure).
  • Remote authentication server: production networks use RADIUS or TACACS+ for centralized user management.

Operational Mode — Command Prefixes

  • show — static snapshot of system/protocol/interface state. Most common exam prefix.

  • clear — reset counters, clear tables, or clear specific protocol state.
  • request — system-level operations (reboot, software upgrade, shell access).

LLDP

LLDP — Link Layer Discovery Protocol

Overview

  • LLDP (Link Layer Discovery Protocol): IEEE 802.1AB standard; allows devices to advertise identity and capabilities to directly connected neighbors.
  • Operates at Layer 2 — discovers devices on the local link only (directly connected, no routing needed).
  • Both devices must have LLDP enabled on the connecting interface to exchange messages.

Information Discovered

  • Neighbor hostname
  • Remote port name/ID (which port the neighbor is connected on)
  • MAC address of the neighbor interface
  • PoE (Power over Ethernet) capability — whether neighbor can supply/receive power via Ethernet cable
  • Vendor name / system description
📌 PoE Definition

PoE (Power over Ethernet): technology delivering electrical power over standard Ethernet cabling alongside data. Common for IP phones, wireless APs, IP cameras.

Layer 2 Protocol

Router-A (MX204)
Chassis MAC: 00:05:86:71:3d:00
Local Port: ge-0/0/0
Periodic LLDPDU Advertisement (Every 30s) Multicast MAC: 01:80:C2:00:00:0E · EtherType: 0x88CC · Hold Time: 120s Vendor-neutral Layer 2 protocol (works across Juniper, Cisco, HP, Arista)
Switch-1 (EX3400)
Chassis MAC: 00:05:86:99:4a:00
Remote Port: ge-0/0/24
Discovered TLV (Type-Length-Value) Attributes:
  • Chassis ID: Neighbor hardware MAC address (00:05:86:99:4a:00)
  • Port ID / Description: Connected remote interface (ge-0/0/24)
  • System Name: Configured neighbor hostname (Switch-1)
  • System Description: OS version (Junos: 22.4R1.10) & hardware model
  • System Capabilities: Supported device roles (Bridge, Router)
  • Management Address: Loopback or OOB management IP (192.168.1.250)
  • IEEE 802.3 PoE: Power over Ethernet allocated wattage & power class
Operational Verification Commands:
show lldp neighbors → Summary table of all adjacent L2 neighbors
show lldp neighbors detail → Comprehensive TLVs (OS, PoE, Management IP, MAC)
⚠ Exam Rule: LLDP operates strictly at Layer 2 — it does NOT require IP addressing configured on the interface!

LLDP Commands

junos — operational mode
show lldp neighbors              # local interface + remote hostname for all neighbors
show lldp neighbors interface xe-0/0/0  # LLDP info for a specific interface
show lldp                        # LLDP global status (timers, enabled/disabled)
💡 General Rule

To verify any protocol: show <protocol-name>. LLDP: show lldp. OSPF: show ospf. BGP: show bgp. Pattern applies universally.

Auto-Completion Details

  • Type first letters, press Space or Tab to auto-complete.
  • If input is ambiguous (matches multiple options), Junos shows all matching completions immediately.
  • Junos stores the fully expanded command in history (not the abbreviation) — making output readable.

Junos CLI Hierarchy

  • All Junos CLI commands and the configuration file follow a tree-like hierarchical structure.
  • Top-level operational keywords: show, monitor, clear, request.
  • Use ? at any level — the CLI is fully self-documenting; no need to memorize everything.
