1
Change the hostname from R1 to router1
Goal: understand that hostname is a single-value field — a new set overrides it; no delete needed first.
Step 1 — Enter configuration mode
root@R1> configure
-- prompt changes from > to # --
root@R1#
Step 2 — Set the new hostname
root@R1# set system host-name router1
Why the prompt still shows R1: The change is staged in the candidate configuration only. The prompt does not update until you commit.
Step 3 — Review your proposed change
root@R1# show | compare
Expected output
[edit system] - host-name R1; + host-name router1;

The - line = what is removed. The + line = what is added. Only this one line should appear.

Step 4 — Commit
root@R1# commit
commit complete
-- prompt now shows the new hostname --
root@router1#

Alternatively, use commit and-quit to save and return to operational mode in one step.

✓ Verification: Prompt reads root@router1#. Run show system host-name to confirm programmatically.
🔍 Troubleshoot: If commit fails, run commit check first to see the specific error. If show | compare shows nothing, you may not have entered the set command correctly.
2
Add IPv6 address 2001:db8:1:2::1/64 to interface xe-0/1/5
Goal: xe-0/1/5 is currently blank. One set command adds unit 0, the address family, and the address simultaneously.
Enter configuration mode (if not already in it)
root@router1> configure
Add the IPv6 address
root@router1# set interfaces xe-0/1/5 unit 0 family inet6 address 2001:db8:1:2::1/64

One command achieves four things: names the interface, sets unit 0, enables family inet6, and assigns the address.

Review the proposed change
root@router1# show | compare
Expected — all additions, no minus signs (interface was blank)
[edit interfaces xe-0/1/5] + unit 0 { + family inet6 { + address 2001:db8:1:2::1/64; + } + }
Commit
root@router1# commit
commit complete
✓ Verification: Run show interfaces xe-0/1/5. Should show Physical link is Up and an inet6 address of 2001:db8:1:2::1/64.
🔍 Troubleshoot: If address doesn't appear, run commit check — an invalid IPv6 address will be caught there before saving.
3
Fix the incorrect IPv4 address on xe-0/1/2: change 172.16.200.1/24 → 172.16.20.1/24
Goal: understand that interfaces support multiple IPs — you must delete the old address explicitly before adding the new one.
⚠ TRAP — The key lesson of Task 3:
Simply running set with the new IP will add it alongside the old wrong address — not replace it. Interfaces can hold multiple IPv4 addresses. You must explicitly delete the old address first.
Step 1 — Confirm the current wrong address
root@router1# run show configuration interfaces xe-0/1/2 | display set | match 172
Expected — reveals just the IPv4 line
set interfaces xe-0/1/2 unit 0 family inet address 172.16.200.1/24
Step 2 — (WRONG WAY, do not commit) Naive approach
-- This demonstrates the trap. Roll back after if you try it. --
root@router1# set interfaces xe-0/1/2 unit 0 family inet address 172.16.20.1/24
What show | compare reveals (the trap)
[edit interfaces xe-0/1/2 unit 0 family inet] address 172.16.200.1/24; ← old wrong IP stays; no minus sign + address 172.16.20.1/24; ← new IP added alongside

Old address has no minus — it stays. Roll back:

root@router1# rollback
Step 3 — CORRECT WAY: delete old, set new
root@router1# delete interfaces xe-0/1/2 unit 0 family inet address 172.16.200.1/24
root@router1# set    interfaces xe-0/1/2 unit 0 family inet address 172.16.20.1/24

Order doesn't matter — both land in the candidate config and deploy together at commit.

Step 4 — Verify before committing
root@router1# show | compare
Expected — clean swap
[edit interfaces xe-0/1/2 unit 0 family inet] - address 172.16.200.1/24; + address 172.16.20.1/24;
Step 5 — Commit and return to operational mode
root@router1# commit and-quit
commit complete
root@router1>
Step 6 — Verify the live interface
root@router1> show interfaces xe-0/1/2
Look for these fields in the output
Physical link is Up ... Protocol inet, Addresses: 172.16.20.1/24 ← correct IP Protocol inet6, Addresses: ← IPv6 still present (untouched)
✓ Verification: 172.16.200.1/24 must NOT appear. Only 172.16.20.1/24 in inet addresses. IPv6 should still be there.
🔍 Troubleshoot: If both IPs appear, you forgot to delete the old one. Go back into config mode, delete the old address, commit again.
4
Find and delete all custom MTU settings across all interfaces
Goal: use a global config search to identify which two interfaces have custom MTU values, then delete just those values.
Step 1 — Search entire config for MTU (operational mode)
root@router1> show configuration | display set | match mtu
Expected — two lines, one per interface
set interfaces xe-0/1/X mtu NNNN set interfaces xe-0/1/Y mtu MMMM -- Exact interface names and MTU values depend on your base config --

This | display set | match pattern is used constantly by Junos engineers. Works for any keyword. Memorize it.

Step 2 — Delete the MTU from both interfaces (config mode)
root@router1> configure
-- Replace xe-0/1/X and xe-0/1/Y with actual names from Step 1 --
root@router1# delete interfaces xe-0/1/X mtu
root@router1# delete interfaces xe-0/1/Y mtu

MTU is the deepest item in its hierarchy path, so no hierarchy trap here — delete operates precisely on it.

Step 3 — Verify with show | compare
root@router1# show | compare
Expected — only minus signs, nothing added
[edit interfaces xe-0/1/X] - mtu NNNN; [edit interfaces xe-0/1/Y] - mtu MMMM;
Step 4 — Commit
root@router1# commit
commit complete
✓ Verification: Run show configuration | display set | match mtu again. It should return no output — no interfaces with custom MTU remaining.
🔍 Troubleshoot: If output still appears, you missed one interface or mistyped the name. Check exact names from Step 1 and re-run the delete.
★
Bonus Drill — Delete xe-0/1/5 entirely using hierarchical delete
Goal: understand why deleting the address ≠ deleting the interface, and how to delete an entire hierarchy branch in one command.
Context (from transcript ~32:32): The customer changed their mind. They don't want xe-0/1/5 right now. Delete all configuration from it. This drill teaches the single most important rule about delete in Junos.
Step 1 — Read the current config before touching it
root@router1> show configuration interfaces xe-0/1/5 | display set
Expected
set interfaces xe-0/1/5 unit 0 family inet6 address 2001:db8:1:2::1/64
Step 2 — (WRONG WAY) Deleting only the address
-- Intuitive but wrong. Roll back after. --
root@router1# delete interfaces xe-0/1/5 unit 0 family inet6 address 2001:db8:1:2::1/64
What show | compare reveals (the trap)
[edit interfaces xe-0/1/5 unit 0 family inet6] - address 2001:db8:1:2::1/64; -- interface, unit 0, and family inet6 are still there --
⚠ Understanding the trap:
delete removes only the deepest item you specify. Deleting the address leaves xe-0/1/5, unit 0, and family inet6 in the config. An interface with family inet6 and no explicit address auto-assigns itself a link-local IPv6 address. The interface is still live even though you wanted it gone. 
-- Roll back the wrong attempt --
root@router1# rollback
Step 3 — CORRECT WAY: delete at the interface level
root@router1# delete interfaces xe-0/1/5

Stopping at xe-0/1/5 causes Junos to delete everything nested under it: unit 0, family inet6, the address — all gone.

Step 4 — Confirm with show | compare
root@router1# show | compare
Expected — entire interface block marked for deletion
[edit interfaces] - xe-0/1/5 { - unit 0 { - family inet6 { - address 2001:db8:1:2::1/64; - } - } - } 
root@router1# commit and-quit
commit complete
✓ Verification: show configuration interfaces xe-0/1/5 returns nothing. show interfaces xe-0/1/5 shows Physical link is Down with no addresses.
Six levels of delete — reference table (from transcript ~36:55):
CommandWhat is deleted
delete interfaces xe-0/1/5 unit 0 family inet6 address 2001:db8:1:2::1/64Only that address; unit, family, interface remain
delete interfaces xe-0/1/5 unit 0 family inet6The inet6 block and its address
delete interfaces xe-0/1/5 unit 0Logical unit 0 and everything under it
delete interfaces xe-0/1/5Entire interface and all config  ✓ this is what you want
delete interfacesEvery single interface on the device
deleteThe entire candidate configuration

Last two are safe in a lab because you still need to commit. Type rollback to undo. Never run these on production.

⚡
Commit Confirmed — Safe remote changes with automatic rollback
Goal: use commit confirmed so that a bad change auto-rolls-back if you don't confirm it, preventing permanent lockout of a remote device.
Scenario (from transcript ~43:22): You are configuring a remote device. If you delete the wrong interface and commit normally, you lose your SSH session — and can't get back in because the interface is gone. commit confirmed solves this.
Syntax — commit confirmed with custom timer
root@router1# commit confirmed 2
commit confirmed will be rolled back in 2 minutes
commit complete

The number is in minutes. Omit for the default of 10 minutes. The transcript example uses 2 minutes.

What happens while the timer runs:
Every time you press Enter, Junos prints a countdown. After zero it auto-rolls-back:
###[ Commit will be rolled back in 2 minutes ]### ###[ Commit will be rolled back in 1 minute ]### ###[ Commit will be rolled back in less than 1 minute ]### commit was not confirmed, automatic rollback complete

Option A — Not happy: do nothing and wait

The rollback fires automatically. Your connection will restore (if disrupted) after rollback completes.

Option B — Happy: confirm and cancel the rollback

-- Any of these cancel the auto-rollback: --
root@router1# commit            -- saves again (creates a 2nd commit entry)
root@router1# commit and-quit   -- saves again, returns to op mode
root@router1# commit check     -- validates only, does NOT save a 2nd time (recommended)
Tip — Why prefer commit check to confirm?
Using plain commit to confirm saves your work twice (once for the original commit confirmed, once for the confirming commit). show system commit then shows two identical-looking entries. If you later need to roll back to the true previous config, you'd need to go to config 2, not config 1. Using commit check validates without saving a second time, keeping your rollback history cleaner.
Power-user: all options combined in one command
root@router1# commit confirmed 2 comment "Changed WAN IP per ticket #4821" and-quit

This single command: commits with 2-min auto-rollback, leaves a comment in commit history, and exits to operational mode.

View commit history (including comments)
root@router1> show system commit
Example
0 2026-08-22 21:45:03 UTC by root via cli Changed WAN IP per ticket #4821 1 2026-08-22 21:40:01 UTC by root via cli 2 2026-08-22 20:10:55 UTC by root via cli
✓ Verification: Run commit confirmed 2 and watch the countdown banners appear each time you press Enter. Type commit check before zero — the banner should disappear, confirming rollback was cancelled.

🚩 Intentional Traps & Things NOT to Fix

⚠ XE-0/1/3 has an incorrect IPv4 address — transcript ~04:48. The course says you will return to it later. Do NOT fix it in this lab. It is deliberately planted.
⚠ Task 3 trap — set does not replace an IPv4 address on an interface
Interfaces hold a list of addresses. Setting a second address adds to the list. The tell is in show | compare: if the old address has no minus sign, it is staying. Always delete the old address first.
⚠ Bonus trap — deleting the address leaves the interface alive with a link-local IPv6
Delete operates on the deepest point you specify. To remove an interface entirely, delete at the interface name level, not the address level.
