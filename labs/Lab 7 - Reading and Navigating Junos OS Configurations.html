📋 Client Audit Scenario: Non-Intrusive Configuration Discovery

Client Organization: Apex Global Enterprise Infrastructure

Device Under Audit: Perimeter Router Router 1 (Juniper MX-204 Universal Routing Platform / Junos OS)

Background: You have arrived on-site as the new network engineer. The previous network administrator departed abruptly, leaving behind several undocumented configuration edits, potential security exposures, and interface parameter discrepancies. Before submitting any changes or maintenance windows, executive management requires a 100% non-intrusive, read-only configuration audit of the live running database.

Core Audit Questions You Must Answer:

  1. Remote Management Services: What administrative protocols are currently active on the device (SSH, Telnet, NETCONF)? Are there plaintext exposures?
  2. User Access & Privileges: What local user accounts exist, what permissions classes are assigned, and is the default root account secured?
  3. Interface MTU Discrepancies: Are there custom Layer 2 (physical Ethernet) or Layer 3 (protocol family) Maximum Transmission Unit values configured on any interfaces?
  4. Discovery Protocol Security: Is Link Layer Discovery Protocol (LLDP) active on internal LAN trunks and correctly isolated from the untrusted public WAN port?

Part 1: Connecting to Router 1 & Verifying Operational State

In this initial phase, you log in to the perimeter router via SSH from your engineering workstation using the active user credentials and verify the operational mode prompt.

Step 1.1: SSH Connection to Perimeter Router

Access

Establish a secure shell connection from your virtual terminal to the perimeter router:

Engineer Workstation — Terminal 
student@workstation:~$ ssh employee@172.16.10.1
Password: **********
Last login: Thu Aug 20 09:45:12 2026 from 172.16.10.50
--- JUNOS 21.4R1.12 built 2026-02-15 08:30:10 UTC
employee@R1>
💡 Instructor Insight: Operational Prompt Breakdown

Notice the prompt: employee@R1>. The format is <username>@<hostname>>.

  • employee: Current authenticated local user account.
  • R1: Active hostname. (Audit Finding: Expected standard is "Router1", but device shows "R1".)
  • >: The angle bracket indicates Operational Mode (read-only inspection, status querying). Configuration mode uses the hash prompt #.

Part 2: Deconstructing the Active Configuration in Set View

In this section, you examine the active configuration database using Set View (| display set). This renders every configuration statement as a linear, self-contained command starting with the set keyword.

CLI Query

Display the entire active configuration formatted as individual set statements:

set system syslog file messages any notice
set system syslog file messages authorization info
set system syslog file interactive-commands commands any
set interfaces xe-0/1/0 description "WAN Internet Connection"
set interfaces xe-0/1/0 unit 0 family inet address 198.51.100.2/30
set interfaces xe-0/1/1 description "Corporate LAN Trunk"
set interfaces xe-0/1/1 mtu 1800
set interfaces xe-0/1/1 unit 0 family inet address 172.16.10.1/24
set interfaces xe-0/1/1 unit 0 family inet6 address 2001:db8:10::1/64

🔍 Instructor Analysis: Set View Anatomy

Notice how every single statement starts with set and reads from left to right: set [hierarchy] [sub-hierarchy] [leaf-parameter] [value].

  • Pro: Compact, grep-friendly, copy-pasteable straight into configuration mode.
  • Pro: Excellent for small and medium configurations.
  • Audit Finding: Note the presence of set system services telnet (unencrypted plaintext management).

🔑 Deep-Dive: System Services & User Privileges

Part 3: Exploring the Configuration in Default Hierarchy View

Junos OS by default displays configuration in Hierarchy View with structured indentation and curly braces { }. This format represents the relational tree stored inside the configuration database.

Step 3.1: View Device Configuration in Default Hierarchy View

CLI Query

Execute the base show configuration command without pipe options:

Router 1 — Operational Mode 
employee@R1> show configuration
version 21.4R1.12;
system {
    host-name R1;
    root-authentication {
        encrypted-password "$6$qP1v$N4k3E6qZ5x8Y0pL9w2M1...";
    }
    services {
        ssh;
        telnet;
        netconf {
            ssh;
        }
    }
    login {
        user employee {
            class super-user;
            uid 2001;
            authentication {
                encrypted-password "$6$zX9a$W1e2R3t4Y5u6I7o8P9...";
            }
        }
    }
    syslog {
        file messages {
            any notice;
            authorization info;
        }
        file interactive-commands {
            commands any;
        }
    }
}
interfaces {
    xe-0/1/0 {
        description "WAN Internet Connection";
        unit 0 {
            family inet {
                address 198.51.100.2/30;
            }
        }
    }
    xe-0/1/1 {
        description "Corporate LAN Trunk";
        mtu 1800;
        unit 0 {
            family inet {
                address 172.16.10.1/24;
            }
            family inet6 {
                address 2001:db8:10::1/64;
            }
        }
    }
    xe-0/1/2 {
        description "Server LAN Trunk";
        unit 0 {
            family inet {
                address 172.16.20.1/24;
            }
            family inet6 {
                address 2001:db8:20::1/64;
            }
        }
    }
    xe-0/1/3 {
        description "Guest LAN Trunk";
        unit 0 {
            family inet {
                mtu 900;
                address 172.16.30.1/24;
            }
            family inet6;

}
protocols {
    lldp {
        interface xe-0/1/1;
        interface xe-0/1/2;
        interface xe-0/1/3;
    }
}
🌟 Instructor Insight: When Hierarchy View Shines

Notice how easy it is to visually grasp the parent-child relationships:

  • On xe-0/1/1, the mtu 1800; line is indented at the physical interface level.
  • On xe-0/1/3, the mtu 900; line is nested inside family inet (Layer 3 only).
  • On xe-0/1/3, family inet6; is a standalone leaf statement with no address child, activating IPv6 link-local addressing only (fe80::).

Part 5: Advanced CLI Pipe Filtering (match, except, count, regex)

On production routers with thousands of configuration lines, piping to filters is essential. This section tests your command formulation skills for fast data extraction.

Step 5.1: Find All Custom MTUs Across All Interfaces

Filter Pipeline

Extract every interface line containing an MTU specification:

Router 1 — Operational Mode 
employee@R1> show configuration interfaces | display set | match mtu
set interfaces xe-0/1/1 mtu 1800
set interfaces xe-0/1/3 unit 0 family inet mtu 900
🎯 Instant Audit Result

In one command, we solved Audit Question #3: exactly two interfaces have custom MTUs configured:

  1. xe-0/1/1: Layer 2 Physical MTU = 1800 bytes.
  2. xe-0/1/3: Layer 3 IPv4 Family MTU = 900 bytes.

Step 5.2: The "Hierarchy Match Trap" (Why Set View is Required)

Critical Gotcha

Observe what happens if you pipe hierarchy view directly to match without display set:

Router 1 — Operational Mode 
employee@R1> show configuration interfaces | match mtu
        mtu 1800;
                mtu 900;
⚠️ Exam & Field Gotcha: Context is Lost in Hierarchy Matching!

In hierarchy view, the interface names (xe-0/1/1, xe-0/1/3) appear on separate parent lines above mtu. When you match on mtu, you only get the isolated leaf lines without knowing which interface they belong to!

Golden Rule: Always pipe to display set FIRST before piping to match: | display set | match <term>.

Step 5.3: Filter for IPv4 Only (Avoiding inet6 Collisions)

Exact String Match

Extract only IPv4 family configurations without capturing family inet6 lines:

Router 1 — Operational Mode 
employee@R1> show configuration interfaces | display set | match "family inet "
set interfaces xe-0/1/0 unit 0 family inet address 198.51.100.2/30
set interfaces xe-0/1/1 unit 0 family inet address 172.16.10.1/24
set interfaces xe-0/1/2 unit 0 family inet address 172.16.20.1/24
set interfaces xe-0/1/3 unit 0 family inet mtu 900
set interfaces xe-0/1/3 unit 0 family inet address 172.16.30.1/24
💡 Syntax Secret: Trailing Space Inside Quotes

Because the string inet is a substring of inet6, running match inet returns both IPv4 and IPv6 lines. Putting quotes around "family inet " with a trailing space ensures strict IPv4 matching.

Step 5.4: Count Interfaces with IPv6 Enabled

Counting Filter

Count how many interface units have IPv6 configured:

Router 1 — Operational Mode 
employee@R1> show configuration interfaces | display set | match inet6 | count
Count: 3 lines

Step 5.5: Multi-Hierarchy Cross-Referencing for an Interface

Global Search

Search across the ENTIRE configuration database for all references to xe-0/1/1:

Router 1 — Operational Mode 
employee@R1> show configuration | display set | match xe-0/1/1
set interfaces xe-0/1/1 description "Corporate LAN Trunk"
set interfaces xe-0/1/1 mtu 1800
set interfaces xe-0/1/1 unit 0 family inet address 172.16.10.1/24
set interfaces xe-0/1/1 unit 0 family inet6 address 2001:db8:10::1/64
set protocols lldp interface xe-0/1/1
🔥 Power Technique: Full-Device Cross-Hierarchy Trace

Notice how this single command extracted lines from both the interfaces hierarchy AND the protocols hierarchy. This proves xe-0/1/1 has LLDP enabled in protocols.

Step 5.6: WAN Discovery Verification (Exclusion Filter)

Except Filter

Confirm what protocols exist while excluding LLDP:

Router 1 — Operational Mode 
employee@R1> show configuration protocols | display set | except lldp

employee@R1> show configuration protocols lldp | display set
set protocols lldp interface xe-0/1/1
set protocols lldp interface xe-0/1/2
set protocols lldp interface xe-0/1/3
🛡️ Security Verification Passed

WAN port xe-0/1/0 is absent from the LLDP protocol hierarchy. Link layer information is not leaking to untrusted upstream ISP networks.
