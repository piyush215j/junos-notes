1. Customer Network Topology & Audit Scenario

As the on-site network engineer for a customer network, your task is to audit and inspect the configuration of their perimeter router (Router 1, a Juniper MX-204 Universal Routing Platform). Previous administrative personnel left behind several configuration discrepancies and security oversights that must be identified through configuration analysis before changes are staged and committed.

Figure 1.1 — Customer Enterprise Topology and Initial Perimeter Router Audit Findings

Audit Objectives & Discovery Tasks

Rather than jumping straight into modifying live device parameters, standard engineering protocol demands a complete non-intrusive audit of the active configuration. The four key discovery questions are:

  1. Remote Management Protocols: Which remote management services are active on the device (SSH, Telnet, NETCONF)?
  2. User Accounts & Privileges: What custom user accounts exist, what permissions classes are assigned, and is the default root account secured?
  3. Custom Interface MTUs: Are there custom Maximum Transmission Unit (MTU) values configured at Layer 2 (physical) or Layer 3 (protocol family)?
  4. Discovery Protocols: Is Link Layer Discovery Protocol (LLDP) enabled on internal LAN ports and properly disabled on the untrusted external WAN port?

2. Junos Configuration Architecture: Active DB vs. Candidate Staging

Unlike monolithic network operating systems (such as legacy Cisco IOS) where every typed command is executed immediately against the live running state, Junos OS implements a robust, database-driven, transactional configuration architecture.

Figure 2.1 — Junos Configuration Transaction Model: Candidate Workspace, Active Database & PFE Push

Core Architectural Concepts

  • Active Configuration: The operational, committed configuration that governs device behavior. It is stored internally in a relational configuration database on the flash drive/SSD. When viewing configurations in operational mode (show configuration), you are querying this active database.
  • Candidate Configuration: A staging copy of the configuration stored in volatile memory (RAM). When an engineer enters configuration mode (configure) and issues set or delete commands, only the candidate configuration is modified. Traffic flow and live operations remain 100% unaffected.
  • Atomic Commit Operation: Executing commit checks syntax across all hierarchies simultaneously, writes the entire state to the active configuration database, and pushes the updated routing/forwarding tables to the Packet Forwarding Engine (PFE). If any part fails validation, the entire commit fails cleanly without leaving partial changes.
  • Configuration Rollback: Junos automatically archives up to 50 previous active configurations (numbered rollback 0 through rollback 49). rollback 0 returns the candidate configuration to the currently active state, discarding uncommitted edits.
📘 Added context: Control Plane (RE) vs. Forwarding Plane (PFE) Separation

Junos is built on FreeBSD-based modular architecture. The Routing Engine (RE) runs user-space management daemons (like mgd for management and configuration, and rpd for routing protocols). The Packet Forwarding Engine (PFE) contains custom ASICs dedicated to line-rate packet switching. When you commit, mgd compiles the new configuration and pushes FIB updates across an internal internal link to the PFE. Even if the RE experiences high CPU or crashes, the PFE continues forwarding established transit traffic without interruption.

⚠️ Common Beginner Mistake: Confusing Uncommitted Edits with Active State

Typing set commands in configuration mode does NOT activate them on the router. Beginners often troubleshoot why a new IP or interface is "not working" before realizing they never issued commit. Conversely, typing show configuration in operational mode only displays what is currently active — to view uncommitted candidate edits, you must use show | compare inside configuration mode.

🛠️ Hands-on Tasks — Section 2

Task 2.1 (Verification): From operational mode, view the active running configuration on the device:

user@Router1> show configuration

Task 2.2 (Scenario Question): An engineer types set system host-name Core-Gateway in configuration mode and disconnects without issuing commit. What is the active hostname of the router, and what happens to the typed command?

Answer: The active hostname remains unchanged (Router1). The uncommitted candidate edit remains in the candidate configuration buffer until committed, overwritten, or discarded via rollback 0.

3. The Two Human CLI Views: Hierarchy View vs. Set View

Although Junos maintains a single active configuration database, it provides two primary human-readable text representations in the CLI: Hierarchy View and Set View.

Figure 3.1 — Structural Comparison: Hierarchy Tree Indentation vs. Linear Set Statements

Detailed Comparison: Hierarchy View vs. Set View

Attribute Hierarchy View (Default) Set View (| display set)
CLI Command show configuration show configuration | display set
Format Structure Indented blocks with opening/closing curly braces ({ }) and terminating semicolons (;). One self-contained command per line, prefixed with the keyword set.
Best Used For Complex, highly nested configurations (BGP policies, firewall filter term conditions, QoS schedulers). Small/compact configurations, rapid CLI copy-pasting, script generation, and line-by-line grep/matching.
Visual Characteristics Expansive white-space; easy to visualize parent-child relationships and scope. High text density; compact screen utilization; potential word-wrap on long strings (e.g. encrypted hashes).
Native Storage Native database representation and default export format on backup servers. Generated dynamically on-the-fly by the Junos parser when requested.
⚠️ Common Beginner Mistake: Over-reliance on Set View

New students frequently rely exclusively on set view because it feels familiar and compact. However, in enterprise and service provider networks with 500-line routing policies or 20-term firewall filters, set view turns into an unreadable wall of text. Professional Junos engineers use both views fluently: hierarchy view for structural comprehension and set view for targeted grepping and script deployment.

4. Junos Top-Level Configuration Hierarchies Overview

Junos organizes all configuration parameters into standardized, top-level functional categories. Regardless of whether you manage an SRX firewall, EX switch, or MX core router, these top-level hierarchies follow an identical organizational model.

Top-Level Hierarchy Primary Purpose & Scope Key Sub-Hierarchies Covered in Transcript
system Device-level parameters, management protocols, user accounts, system logging, time/NTP, and authentication. host-name, services, login, root-authentication, syslog
chassis Hardware-specific attributes, port aggregation speeds, FPC/PIC redundancy, and power management. fpc, pic, redundancy
interfaces Physical port properties (speed, MTU, descriptions) and logical protocol units (unit 0, family inet, family inet6). xe-0/1/0 through xe-0/1/3, unit, family
protocols Configuration and activation of Layer 2/3 protocols (discovery, spanning tree, dynamic routing, MPLS). lldp, rstp, isis, mpls, bgp, ospf
📘 Added context: Additional Junos Top-Level Hierarchies for JNCIA-Junos

In addition to the core four covered above, JNCIA-Junos candidates should recognize:

  • routing-options: Static routes, default gateways, Router ID, Autonomous System (AS) number.
  • firewall: Stateless packet filtering rules, terms (match/then actions), and policers.
  • policy-options: Routing policy statements (prefix lists, BGP community maps, AS-path filters).
  • security: Stateful firewall policies, security zones, and NAT (specifically on SRX Series).

⚠️ Key Architectural Distinction: Interface Properties vs. Protocol Bindings

A fundamental Junos design rule: Interface configuration belongs under interfaces, but running a protocol over that interface belongs under protocols. For instance, IP addresses and MTUs are configured under interfaces xe-0/1/1 unit 0, while enabling LLDP or OSPF on that link is configured under protocols lldp interface xe-0/1/1. This guarantees all protocol settings remain consolidated in a single hierarchy.

5. Deconstructing the system Hierarchy

The system hierarchy contains all foundational settings required for device identification, administrative access, user permissions, and auditing.

Figure 5.1 — Decomposition of the Junos OS system Configuration Tree

1. Hostname Configuration

set system host-name R1

Defines the system identity displayed in the CLI prompt (e.g. employee@R1>). To fix the customer requirement, this will be modified to Router1.

2. Management Services (SSH, Telnet & NETCONF)

set system services ssh
set system services telnet
set system services netconf ssh
  • ssh: Enables secure shell access over TCP port 22 with encrypted transport.
  • telnet: Enables unencrypted cleartext access over TCP port 23. Security Risk In production, Telnet should always be disabled.
  • netconf ssh: Activates the XML-based Network Configuration Protocol over SSH subsystem (TCP port 830), allowing automated Python/Ansible scripts and base config loaders to manipulate device state programmatically.

3. User Accounts, Password Encryption & Login Classes

set system login user employee class super-user
set system login user employee authentication encrypted-password "$6$b7zY..."
set system login user employee uid 2001
  • Login Classes: Determine the permission matrix for the user:
    • super-user: Full access to all configuration and operational commands (root-equivalent).
    • operator: Can view configuration and clear/reset network counters, but cannot modify configuration.
    • read-only: View-only access across operational and configuration modes.
    • unauthorized: Blocked from executing commands.
  • Interactive Passwords vs. Stored Hashes: When configuring a password in the CLI (set system login user employee authentication plain-text-password), Junos prompts for plaintext input, hashes it with a one-way salt (SHA-512 / $6$), and stores only the resulting hash in the configuration.
  • User ID (UID): An internal Unix system identifier. If omitted during manual configuration, Junos automatically generates and assigns a unique UID.

4. Root Authentication

set system root-authentication encrypted-password "$6$k8Lp..."

Sets the administrative password for the built-in root account (UNIX UID 0). Junos enforces a strict mandatory security rule: a factory-default Junos device will reject any initial commit if a root authentication password has not been configured.

5. System Logging (syslog)

set system syslog file messages any notice
set system syslog file messages authorization info
set system syslog file interactive-commands commands any

Junos provides standard pre-defined system log files stored in /var/log/:

  • file messages: Captures all system events at severity notice and higher, plus all user authentication events at severity info and higher.
  • file interactive-commands: Logs every operational and configuration command executed by users for auditing and compliance.
📘 Added context: Junos Syslog Severity Hierarchy

Junos adheres to standard BSD syslog severity levels from highest (0) to lowest (7):
emergency (0) > alert (1) > critical (2) > error (3) > warning (4) > notice (5) > info (6) > debug (7).
Configuring a level logs that level and all higher severities (e.g., notice captures notice, warning, error, critical, alert, and emergency).

6. Deconstructing the interfaces Hierarchy

The interfaces hierarchy defines both the physical hardware layer (Media Access Control, port framing, Layer 2 MTU) and the logical layer (Logical Units, Protocol Families, IP Addressing, Layer 3 MTU).

Figure 6.1 — Juniper MX-204 Hardware Port Layout & Detailed Interface Parameter Anatomy

1. Physical vs. Logical Interfaces (unit 0)

In Junos, hardware ports are referenced as physical interfaces (e.g. xe-0/1/1). However, IP protocol stacks cannot be bound directly to a physical interface. Junos requires a logical unit (typically unit 0 for single untagged connections) to host address families.

set interfaces xe-0/1/1 description "Corporate LAN"
set interfaces xe-0/1/1 unit 0 family inet address 172.16.10.1/24
set interfaces xe-0/1/1 unit 0 family inet6 address 2001:db8:10::1/64

Notice that Junos uses CIDR slash notation (/24, /64) directly instead of legacy dotted-decimal subnet masks (255.255.255.0).

2. Physical MTU (Layer 2) vs. Protocol Family MTU (Layer 3)

Understanding MTU configuration levels is essential for network reliability:

Figure 6.2 — Packet/Frame Encapsulation: Physical Layer 2 MTU vs. Protocol Family Layer 3 MTU
  • Physical Interface MTU (set interfaces xe-0/1/1 mtu 1800): Specifies the maximum Ethernet frame size (including L2 header, payload, and FCS) that the physical transceiver and ASIC will transmit or receive.
  • Family MTU (set interfaces xe-0/1/3 unit 0 family inet mtu 900): Caps the maximum IP packet size (IP header + payload) strictly for IPv4 packets. IPv6 packets on the same logical interface are unaffected and adhere to the default interface MTU.

3. IPv6 Link-Local Only Configuration (family inet6)

set interfaces xe-0/1/3 unit 0 family inet6

When family inet6 is enabled without specifying an explicit IPv6 address, Junos automatically provisions an IEEE EUI-64/modified link-local address (fe80::/64). In core enterprise and ISP transit networks, this is a standard design best practice: routing protocols (like IS-IS or OSPFv3) form neighbor adjacencies across link-local addresses, while edge devices communicate using stable, always-on loopback (lo0.0) IPv6 addresses, completely eliminating transit link IP subnet administration.

⚠️ Common Gotcha: MTU Mismatches Cause Silent Failures

A mismatch between Layer 2 and Layer 3 MTUs can cause insidious network issues. Small ICMP pings succeed, but large data transfers (TCP MSS negotiation failures, Path MTU Discovery blackholes) or routing protocol adjacency handshakes (such as OSPF DBD exchange getting stuck in EXSTART/EXCHANGE state) fail silently.

🛠️ Hands-on Tasks — Section 6

Task 6.1 (Audit Command): Use the CLI to display only interface xe-0/1/1 in hierarchy view:

user@Router1> show configuration interfaces xe-0/1/1

Task 6.2 (Verification Question): If an engineer sends a 1200-byte IPv6 packet and a 1200-byte IPv4 packet out of interface xe-0/1/3, what happens to each packet?

Answer: The IPv6 packet traverses successfully (subject to the 1500-byte default L2 MTU). The IPv4 packet is fragmented or dropped with "Packet Too Big" ICMP message because IPv4 is explicitly restricted to mtu 900 under family inet.

7. Deconstructing the protocols Hierarchy

Figure 7.1 — The protocols Hierarchy: LLDP Architecture, Neighbor Discovery Model, and Protocol Binding Syntax

The protocols hierarchy contains all protocol-specific operational states, timer adjustments, and interface bindings.

1. Link Layer Discovery Protocol (LLDP - IEEE 802.1AB)

set protocols lldp interface xe-0/1/1
set protocols lldp interface xe-0/1/2
set protocols lldp interface xe-0/1/3
  • Physical Binding: Notice that LLDP is enabled on physical ports (xe-0/1/1) rather than logical units (unit 0). This is because LLDP is a Layer 2 discovery protocol operating directly over Ethernet frames.
  • WAN Security Boundary: Interface xe-0/1/0 (the WAN connection to the Internet) is intentionally excluded from the LLDP hierarchy to avoid broadcasting internal system details, chassis models, and software revisions to untrusted external networks.

2. Protocol Hierarchy Uniformity across Junos OS

Junos adheres to an intuitive, predictable command grammar across virtually all networking protocols:

set protocols rstp interface xe-0/1/1      # Rapid Spanning Tree Protocol (L2 loop prevention)
set protocols isis interface xe-0/1/1      # Intermediate System to Intermediate System (L3 IGP)
set protocols mpls interface xe-0/1/1      # Multiprotocol Label Switching (L2.5 label switching)

Once you understand how to bind interfaces and configure parameters for one protocol, navigating other advanced protocols becomes second nature.

8. Sub-Hierarchy Scoping & Targeted Navigation

On large production routers running thousands of lines of configuration, viewing the entire configuration is inefficient. Junos allows you to scope your show configuration query directly to any specific branch or sub-hierarchy level.

Target Configuration Area Scoped Hierarchy Command Equivalent Scoped Set Command
System Services (SSH, Telnet, NETCONF) show configuration system services show configuration system services | display set
User Login Accounts & Classes show configuration system login show configuration system login | display set
Single Specific Interface (xe-0/1/2) show configuration interfaces xe-0/1/2 show configuration interfaces xe-0/1/2 | display set
Specific User Account (employee) show configuration system login user employee show configuration system login user employee | display set
LLDP Protocol Only show configuration protocols lldp show configuration protocols lldp | display set
📘 Added context: Truncation Behavior in Hierarchy Scoping

When executing show configuration interfaces xe-0/1/2 in hierarchy view, Junos automatically skips the outer interfaces { xe-0/1/2 { ... } } headers in the output, starting the indented display directly at unit 0. This intelligent truncation maximizes terminal space and readability.

9. Advanced CLI Output Filtering with Pipes (|)

The Junos CLI contains a powerful UNIX-style text processing pipeline that allows engineers to filter, transform, count, and isolate specific configuration parameters instantly.

Figure 9.1 — The Junos CLI Pipe Data Processing Pipeline

Essential Pipe Filter Actions

  • | display set: Converts hierarchical output into linear set commands.
  • | match <regex/text>: Includes only lines containing the specified case-insensitive regular expression/string (equivalent to Unix grep).
  • | except <regex/text>: Excludes lines containing the specified string (equivalent to Unix grep -v).
  • | count: Returns only the total number of lines matched.

High-Yield Real-World Diagnostic Examples

1. Auditing All Custom MTUs Across Every Interface:

user@Router1> show configuration interfaces | display set | match mtu
set interfaces xe-0/1/1 mtu 1800
set interfaces xe-0/1/3 unit 0 family inet mtu 900

2. Finding All References to an Interface Across the ENTIRE Device:

user@Router1> show configuration | display set | match xe-0/1/1
set interfaces xe-0/1/1 description "Corporate LAN"
set interfaces xe-0/1/1 mtu 1800
set interfaces xe-0/1/1 unit 0 family inet address 172.16.10.1/24
set interfaces xe-0/1/1 unit 0 family inet6 address 2001:db8:10::1/64
set protocols lldp interface xe-0/1/1

This single command searches across interfaces, protocols, firewall, and policy-options simultaneously, preventing the engineer from having to hunt across individual hierarchies.

3. Filtering IPv4 vs. IPv6 Address Families:

⚠️ CLI Filtering Tip: The Space in "family inet "

Because the string inet is a substring of inet6, running | match inet matches both IPv4 and IPv6 lines. To isolate only IPv4 configurations, include a trailing space inside quotes: | match "family inet ".

user@Router1> show configuration interfaces | display set | match "family inet "

11. JNCIA-Junos Exam Cheat Sheet & Key Takeaways

Figure 11.1 — Summary Concept Matrix for JNCIA-Junos Certification
Core Concept / Exam Question Focus Correct Junos Architecture Behavior
Where do uncommitted changes live? In the Candidate Configuration in RAM. They have zero effect on live network operations until committed.
What is the default configuration display format? Hierarchy View (indented tree blocks with curly braces). Set format is generated on the fly via | display set.
How are IPv4 and IPv6 address families denoted? family inet for IPv4, and family inet6 for IPv6.
What happens if physical MTU is 1800 and family inet MTU is 900? The physical interface supports frames up to 1800 bytes. IPv4 packets are capped at 900 bytes, but IPv6 packets can use up to the physical frame limit.
Why is LLDP configured under protocols and not interfaces? Junos maintains strict architectural separation: interface parameters live under interfaces, while protocols running across those interfaces live under protocols.
How do you search for an interface across all hierarchies? show configuration | display set | match <interface-name>
